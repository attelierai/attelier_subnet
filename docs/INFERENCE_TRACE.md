# H3 trusted trace/render scoring v1

`trace_trusted_render` is an opt-in scoring mode. It does not reinterpret
existing reference-mode batches or historical weights. It is a closed,
qualified profile policy, not a proof of remote GPU ownership or a general
claim that a matching video was independently generated by a miner.

## Trust boundary and envelope

Before the worker POST, the validator commits a canonical request binding:
`jobId`, validator nonce, canonical parameters/input hash, target lane
(`hotkey`, `workerId`, profile id/hash, trusted-renderer hash), and request
time. This prevents a later result from being reassigned to another request or
lane.

After execution, but before audit selection, the worker/validator custody path
commits an envelope with schema `forge-h3-trace/v1`. Its trace payload is a
manifest containing an ordered `chunks` list; every entry has its SHA-256
digest. It is intentionally not described as a Merkle commitment. The envelope
also binds the request fields, model/workflow parameters, final latent chunk
references, and result binding. A raw capture manifest is only auxiliary
evidence: it is not by itself a request authority, qualified profile, or
trusted trace commitment.

The trusted verifier checks the requested full 20-step profile, selected model
replays and recurrence/input bindings against the committed chunks. The trusted
renderer renders the accepted final latent and binds delivered media to that
renderer output. Its single result is one of:

- `verified`: full20 evidence and trusted rendering succeeded.
- `invalid`: a validator established a miner-attributed fault.
- `inconclusive`: custody, renderer, platform, or unsupported-profile evidence
  was insufficient; it is not a miner strike.

`timeout` and `busy_capacity` are miner faults only when the validator has
assigned that attempt to the miner lane. Platform-owned failures remain
`inconclusive`. `pending` is awaiting bounded re-audit and receives no new
credit.

## Qualification, window, and score

An external qualification registry (not miner metadata) must attest the exact
lane:

```json
{
  "hotkey": "…",
  "workerId": "…",
  "profileId": "h3-native-blackwell-20-v1",
  "profileHash": "…",
  "rendererHash": "…"
}
```

It has an expiry. A change of any lane field is a new qualification, not a
transfer of history. Each scoring window freezes `minCompleted`, `minVerified`,
start/end timestamps, and the scoring policy. Pilot values are four completed
attempts and two verified attempts; no profile is eligible merely because those
numbers are configured.

For an active qualified lane with the frozen coverage minimums:

`A = verified / (verified + confirmedMinerFault)`

`S = mean(referenceSeconds / (referenceSeconds + workerSeconds))` over
verified attempts with finite timings; no usable timing gives `S = 0`.

`rewardScore = A * (0.8 + 0.2 * S)`

Platform-inconclusive and pending attempts are outside `A`'s denominator. They
do not create automatic credit, but neither strike the miner nor erase a
previously qualified estimate. A pending re-audit whose deadline expires
suspends fresh admission for that lane only while retaining already measured
availability/speed facts; it does not globally block other miners or rewrite
trusted history. Qualification expiry blocks new certification while retaining
facts; window expiry ends eligibility normally. A complete all-fault window
reports its measured zero rather than disguising it as missing coverage.
Confirmed miner faults affect only the corresponding lane and count zero for
that job, rather than zeroing the miner's whole historical window.

The user-facing TTV is gateway-to-available-video and includes queue, audit and
trusted render time. It is reported separately from worker speed so platform
delays are not silently charged to a miner. The current scorer exposes a median
only for verified deliveries; service/reporting must label it accordingly.

## Claim limits and rollout gate

The launch gate is a separately qualified profile, a fresh frozen window, and
full20 verification for every credit-bearing attempt. Organic jobs may be
supplemented by probes; no partial trace result earns this mode's credit.
Inconclusive rows may be re-audited inside their declared deadline but cannot
be converted to verified by metadata or timing alone.

This design detects only failures covered by committed evidence and trusted
replay/renderer checks. It does not establish GPU ownership, prevent a miner
from outsourcing work, or turn a small calibration into a population guarantee.

## Verifier candidate revision: lane custody and measured renderer

This revision is prepared code, not a GPU qualification or an activation of the
public gateway. The experimental validator requires an operator-owned
`qualification.lanes` list in the profile envelope. Each element is exactly the
five-field lane shown above. The envelope's evidence hash and expiry apply to
those listed lanes only; a globally qualified profile does not admit an unlisted
worker. The validator stores the complete lane with each SQLite intent, checks
it again before dispatch and evidence download, and does not transfer historical
credit when a configured hotkey or worker changes. Older intents without that
snapshot cannot earn new trace-mode credit. Existing reference-mode records are
unchanged.

Both trusted runtime CLIs require `--hotkey` from the operator's frozen lane,
not from browser parameters. They independently enforce the same lane registry
before remote work and emit `lane` on their bound report. Consumers must compare
that field to their saved intent. The Python validator and diagnostic harness
use this contract; the API adapter's argument/report binding update belongs to
the coordinator. Old API invocations fail closed until integrated.

Startup measurements now emit `forge-h3-runtime-attestation/v2`, including
`rendererHash`. The verifier checks the measurement hash, the exact installed
verifier source set, workflow, FFmpeg version and renderer fingerprint before
submitting a GPU graph. Old v1 attestations and changed source are inconclusive;
regenerate the measurement and freeze a new profile instead of copying a former
qualification. The profile still pins the checkpoint hashes measured at startup.
This remains an operator-controlled runtime: it is not remote hardware
attestation, and immutable source/checkpoint custody is an operating requirement.

A signed capture must bind its schema, run id, input hash, numerical profile,
20 declared/callback steps and 20 forward bundles before costly reference work.
After an independent trusted baseline succeeds, an actual disagreement in
inputs, outputs, schedule or the 20 predictions is `invalid` under that frozen
bit-exact contract. Unavailable tensors, broken baseline execution, unsupported
profiles or failed runtime/renderer measurement remain `inconclusive`. Diagnostic
mode always demotes the public verdict to `inconclusive`, retaining a separate
`diagnosticVerdict`; it never exports a verified result path or final latent.

The CPU integration exercises signed stored tensors, actual verifier subprocess,
loopback HTTP and real FFmpeg/FFprobe. It covers an honest trajectory, omitted
call at step 7, changed final latent, fewer callbacks, stale request, unavailable
GPU and diagnostic suppression. Only the external Comfy endpoint is simulated;
no H3 model computation occurs. The resulting media is the fixture trusted
renderer's re-encoded 120-frame, five-second output, never the supplied miner
file. This proves the local runtime boundary, not production client delivery.

## Next GPU decision and acceptance gate

The next experiment can decide whether one exact verifier profile is suitable for
a bounded private lane qualification. It cannot prove population-wide
false-accept rates, GPU ownership, absence of outsourcing, cross-device
portability, or eligibility of arbitrary miners.

Freeze evaluator sources, checkpoint lock, dependency lock, recurrence threshold,
request parameters, prompt lineages and the complete case matrix before running
holdout. After startup measurement, freeze both lanes' exact profile and renderer
hashes before their first holdout. If the measurements differ, stop as unsupported;
do not widen a tolerance or rewrite the profile after inspecting results.

Use two isolated operator-controlled devices: miner and validator/renderer.
Restrict requests to base T2V, 832x480, 5 seconds, 24 fps,
audio, res_multistep/simple, CFG 1 and 20 calls. Use one separate development
smoke lineage, then three new holdout lineages. For each holdout lineage:

- Two honest requests for the same prompt with distinct job ids/nonces and
  derived seeds. Each is replayed on the validator with exactly its own inputs;
  an idempotent cached response is not an independent honest repetition.
- One capture with a skipped model call, one real shorter schedule, and one
  freshly signed altered-final-latent bundle.
- One substituted miner MP4 paired with valid evidence: the private test client
  must receive trusted-renderer bytes, never those miner bytes. This is a custody
  PASS, not an expectation that an ignored MP4 makes a valid latent invalid.
- One old signed receipt replayed against a fresh nonce/derived seed; it must be
  rejected before GPU submission.

These are 21 holdout evaluations, grouped into three independent prompt lineages,
plus one smoke. Repeated rows and derived attacks are correlated, not 22
independent samples. All six honest controls must satisfy exact full20 checks;
all nine trace/model mutations and all three stale requests must be rejected;
all three miner-media substitutions must yield the exact trusted output at the
client. Any honest false rejection or accepted bad trace is FAIL. Missing rows,
unsupported profiles, infrastructure failures or missing client-delivery evidence
are INCONCLUSIVE; no partial set qualifies. Retain per-stage timings, bytes,
request/receipt/profile/renderer bindings and raw receipts. No threshold tuning
or automatic repeat campaign is permitted after seeing holdout failures.

The single-runtime smoke/attack harness remains a diagnostic tool. The separate
`scripts/h3_two_lane_qualification.py` executes the frozen matrix: the validator
pulls signed evidence through the configured transport, verifies it locally, and stops at
the first failed case or its deadline. The `client` command receives and hashes
the actual trusted media stream on an independent control host without retaining
media there. Its receipt proves only this private experimental transport.

Both runtime adapters support `--export-diagnostic-artifact` only together with
`--allow-unqualified-diagnostic`. The separate private manifest binds a fixed
`result.mp4` name, hash and size to the inconclusive public report. The transport
adapter validates that binding and fetches it as `diagnostic-result.mp4`; the public report
still carries no `result` or `finalLatent`. This export never qualifies a profile
or enables service credit. Production API delivery and integration remain owned
by the coordinator and require their own evidence. No campaign or expenditure
is authorized by this document.

The pinned Comfy `SaveVideo` node returns its MP4 through `outputs["7"].images`,
with `type: "output"`. Resolve exactly one such relative filename below the owned
output directory; reject paths escaping it. `gifs`/`video` fixtures do not model
this pinned wire contract. A parser change still changes the renderer/runtime
fingerprint and requires fresh measurement and qualification.

Capture roots may be mounted through a symlink; receipt signing resolves the
root before checking containment. An explicitly hash-pinned, completed but
unscored development smoke can be sealed without regenerating it. This recovery
is forbidden for holdout cases, preserves the original capture and failed-run
receipts, and requires a new frozen runner/plan before holdout starts. It does
not count as another honest generation or erase the failed attempt.

## Offline acceptance and permissionless decision

Keep serving whitelisted. Full replay plus trusted rendering remains the narrow
candidate for a future **exact-lane** qualification; it is not permissionless
admission. Historical partial campaigns do not close the complete matrix,
client delivery, restart or independent control reads. Historical shutdown or
archive receipts do not establish current provider, storage, production or cost
state.

The offline receipt analyzer rejects reused honest calibration captures by both
capture `runId` and manifest digest, including a manifest copied to a new path.
Calibration and holdout must have disjoint declared generation lineages. These
checks apply when freezing calibration and when reading it for a report; an old
freeze cannot exempt a contaminated set. Rejection is `INCONCLUSIVE`, with no
calibration output or miner accusation. Unique IDs/hashes alone do **not** prove
independent generation: operator custody and a frozen lineage plan remain trusted.
Derived adversaries and repeated frames/steps never increase independent sample
count. This analyzer emits research results, not a qualified profile envelope.

### Threat model and alternatives

| Threat or alternative | Decision and limit |
| --- | --- |
| Replay or substitution of claims | Bind job, worker, nonce, derived seed, parameters, model, workflow, runtime and exact profile; receipt signatures authenticate those declarations, not their truth or physical executor. |
| Omitted calls, altered tensors, swapped miner media | Require full20 replay/input/recurrence evidence and bind delivered bytes to the trusted renderer. A missing file/unsupported platform is inconclusive; only an established miner-attributed fault is invalid. |
| Corrupt operator/verifier, registry, or mutable runtime | Remains outside this operator-trusted design's protection. Source measurements are not hardware attestation. Bind qualification to exact lane/profile/renderer and expiry; changed fields require fresh qualification. |
| Sampling as a cheaper verifier | Under uniform sampling without replacement, detection of k altered steps among 20 by 3 samples is `1 - C(20-k,3)/C(20,3)`. For one altered step it is 15%, conditional on detectable disagreement and unpredictable selection after commitment. Predictable samples weaken it further. No full-verification or credit claim. |
| Perceptual quality/fidelity scoring | VBench measures video quality and condition consistency [1]. It cannot establish which checkpoint or 20-step computation produced a plausible video (our inference). Keep quality evaluation separate from computation/custody gates. |
| TEE plus verified linear work | Slalom delegates linear layers from SGX to an untrusted GPU [2]. Its authors label the implementation a research prototype. Adapting it to H3 operators, nonlinearities and the full render pipeline would require a new evaluated implementation; it is not a drop-in shortcut. |
| CPU/GPU confidential-compute attestation | NVIDIA requires supported hardware/software, GPU evidence and a CPU/workload trust policy [3]. A valid GPU quote alone does not validate the workload. This is a possible different trust model, with fresh nonce and output/key binding required; compatibility of our devices is unverified. |
| Cryptographic computation proof | zkLLM proves a specified LLM computation [4]. It does not supply an H3 video circuit or prove our floating-point/codec pipeline. Investigate only after specifying arithmetic, weights, all operators and output binding; no H3 cost or feasibility claim follows from its benchmarks. |
| Cross-device comparison | PyTorch does not guarantee reproducibility across versions/platforms or CPU/GPU [5]. Freeze exact hardware/runtime/numerics and qualify each lane; never infer portability or widen tolerance after a holdout failure. |

The chosen next decision is whether the frozen operator-controlled two-lane
candidate passes its private acceptance matrix. None of the alternatives above
currently justifies opening arbitrary miner admission, proving physical GPU
ownership, or asserting absence of outsourcing. Outsourcing can produce entirely
valid computation evidence; it is not excluded by a signed receipt.

### Future experiment completion and recovery gate — not executed or funded

Keep the two-device, one development smoke plus three-new-lineage/21-holdout
matrix above. Do not resume the five old rows to create a newly independent
holdout. Freeze a new plan and exact measured profiles before any new holdout;
the previous v7 record remains unchanged. Stop on profile mismatch, an honest
false rejection, a wrongly accepted bad trace, or inability to complete within
the approved closing reserve. Do not retune thresholds or automatically retry.

After all six honest, nine trace mutations, three stale requests and three media
substitutions meet their expected outcomes, an independent client must receive,
hash, probe and fully decode every accepted trusted output. Bind each receipt
to plan/case/job/request/receipt/profile/lane/renderer/report and delivered bytes.
For the three substitutions, demonstrate that delivered bytes are the trusted
render, not the submitted miner media. Missing custody makes qualification
inconclusive even when all numerical diagnostics match.

In an isolated private API environment owned by its coordinator, record delivery,
perform the planned restart, then make independent control GETs for the same
jobs. Require unchanged identity, terminal verdict and exact media hash/size,
no new inference, and preserved inconclusive/invalid cases. Lost evidence stays
inconclusive; restart must not promote a diagnostic report or replay a charge.
Back up the complete evidence to the authorized private location and verify
full readback hashes before closing workers. Record closure separately from
backup completeness. These live gates are pending, not covered by CPU fixtures.

Before requesting any resources, quote bootstrap, measurement, smoke, all cases,
client delivery/decode, restart/control GET, archive/readback and closure reserve.
Use a fixed USD ceiling and a time feasibility preflight; reserve two per-case
timeouts plus archive/closure time before starting another case. Historical
pipeline timings are planning observations, not a serving benchmark or price.
**Cost: not quoted; spending and GPU execution: not authorized.** This proposal
contains no production operation and does not change the serving whitelist.
